# University of the People Computer Science Students

Welcome to the **University of the People Computer Science Students GitHub Organization**.

This organization is a collaborative space for **University of the People (UoPeople) Computer Science students and contributors** to learn, build, experiment, collaborate, contribute to open source, and create software projects together.

The goal is simple:

> **Learn together. Build together. Review each other’s work. Create real projects. Grow as software engineers.**

University coursework gives students theoretical and practical foundations, but collaboration and real-world software development require additional experience.

This organization exists to help bridge that gap.

Here, students can work on projects, contribute to existing repositories, participate in code reviews, learn modern development workflows, improve their GitHub profiles, and gain experience working with other developers.

# 🎯 Our Mission

The mission of this organization is to create a collaborative technical community where University of the People Computer Science students can gain practical software engineering experience.

We aim to help members:

* Build real-world software projects.
* Learn Git and GitHub collaboration.
* Work with other developers.
* Participate in code reviews.
* Learn how open-source projects operate.
* Improve problem-solving skills.
* Explore different programming languages and technologies.
* Build a public portfolio.
* Gain experience contributing to shared codebases.
* Learn software engineering best practices.
* Improve technical communication.
* Learn from mistakes in a supportive environment.

This organization is not intended to replace University coursework.

Instead, it provides an environment where students can apply what they learn and explore software development beyond individual assignments.

# 🧭 Our Core Principles

Every contributor is expected to follow these principles.

## 1. Learn in Public

It is okay not to know something.

Ask questions.

Make mistakes.

Learn from reviews.

The goal is not to appear perfect.

The goal is to improve.

---

## 2. Collaboration Over Competition

This is a collaborative community.

We encourage members to:

* Help other contributors.
* Share knowledge.
* Review code.
* Explain technical concepts.
* Provide constructive feedback.

Success should not come at the expense of other contributors.

---

## 3. Respect Every Skill Level

Some contributors may be writing their first program.

Others may already have professional software engineering experience.

Both belong here.

Never mock, insult, or discourage someone because of their experience level.

---

## 4. Quality Matters

Projects should not become collections of unmaintained or low-quality code.

We encourage:

* Clear architecture.
* Meaningful documentation.
* Testing where appropriate.
* Code reviews.
* Consistent coding standards.
* Maintainable solutions.

---

## 5. Ownership Matters

If you volunteer to work on something, communicate clearly.

If you cannot continue working on it, let the team know.

Do not disappear while blocking important work if communication is possible.

```text

├── developer-tools/
├── data/

```

Individual repositories may have their own:

* Maintainers.
* Contribution guidelines.
* Technology stacks.
* Coding standards.
* Development workflows.

Repository-specific rules may add additional requirements.

When repository-specific rules conflict with general organization rules, contributors should follow the repository-specific rules unless otherwise stated.

---

# 📁 Repository Rules

Every repository should have a clear purpose.

At a minimum, active project repositories should aim to include:

```text
README.md
LICENSE
CONTRIBUTING.md
CODE_OF_CONDUCT.md
SECURITY.md
```

Depending on the project, repositories may also include:

```text
docs/
tests/
.github/
```

The repository README should explain:

* What the project does.
* Why the project exists.
* The technology stack.
* Installation instructions.
* Configuration requirements.
* How to run the project.
* How to contribute.
* How to report bugs.
* License information.

---

# 💡 Starting or Proposing a Project

Before creating a new repository, contributors should consider whether a similar project already exists.

Avoid creating multiple repositories for the same idea without discussion.

A project proposal should ideally explain:

## Project Name

What will the project be called?

## Problem

What problem does the project solve?

## Target Users

Who is expected to use it?

## Proposed Technology

For example:

```text
Frontend: React
Backend: Go
Database: PostgreSQL
Infrastructure: Docker
```

The technology stack should not be chosen simply because it is popular.

It should be appropriate for the project.

## Initial Scope

The project should begin with a realistic scope.

Avoid attempting to build an extremely large system before validating the basic idea.

A smaller MVP is often better.

---

# 🤝 Contributing to Projects

Before contributing:

1. Read the repository README.
2. Read the `CONTRIBUTING.md` file.
3. Check existing issues.
4. Check whether someone is already working on the issue.
5. Ask questions if requirements are unclear.

Do not begin major changes without understanding the project structure.

# 🌿 Git and Branching Rules

Direct pushes to protected branches are not allowed.

For most projects, the primary branches will be:

```text
main
develop
```

The exact workflow may vary depending on the repository.

Contributors should create a branch for their work.

Example:

```bash
git checkout -b feature/user-authentication
```

Other examples:

```text
feature/add-user-profile
feature/payment-integration

fix/login-validation
fix/api-timeout

docs/improve-installation-guide

refactor/database-layer

test/add-authentication-tests
```

Branch names should clearly describe the purpose of the work.

Avoid names such as:

```text
test
new
update
mybranch
job
changes
```

---

# 📝 Commit Message Guidelines

Commit messages should clearly describe what changed.

Good examples:

```text
feat: add user authentication
fix: resolve login validation issue
docs: improve installation instructions
test: add tests for authentication service
refactor: simplify database connection logic
```

Avoid commit messages such as:

```text
update
fix
changes
done
final
test
asdf
```

A commit should represent a meaningful change whenever possible.

Avoid combining unrelated changes into one commit.

---

# 🔀 Pull Request Guidelines

All significant contributions should be submitted through Pull Requests.

A Pull Request should clearly explain:

* What changed.
* Why the change was necessary.
* How the change was tested.
* Any important implementation decisions.
* Any limitations or known issues.

A good Pull Request description might include:

```markdown
## What does this PR do?

Adds authentication using JWT.

## Why?

The application previously allowed access to protected endpoints.

## Changes

- Added authentication middleware.
- Added JWT validation.
- Added login endpoint.
- Added authentication tests.

## Testing

- Added unit tests.
- Tested protected endpoints manually.

## Screenshots

Add screenshots if the change affects the UI.
```

---

# 👀 Code Review Rules

Pull Requests may be reviewed by maintainers or other contributors.

Reviews are intended to improve:

* Code quality.
* Security.
* Maintainability.
* Readability.
* Architecture.

Review comments should focus on the code.

Do not attack the contributor.

Good feedback:

> This function appears to handle multiple responsibilities. Would it make sense to separate the validation logic from the database logic?

Poor feedback:

> This code is terrible.

Always explain suggestions when possible.

# 🐛 Issue Guidelines

Issues should be used for:

* Bug reports.
* Feature requests.
* Documentation problems.
* Performance issues.
* Security concerns.
* Project discussions.

Before opening an issue:

1. Search existing issues.
2. Check whether the problem has already been reported.
3. Provide enough information to reproduce the problem.

A good bug report should include:

```text
Expected behavior:
What should happen?

Actual behavior:
What actually happens?

Steps to reproduce:
1.
2.
3.

Environment:
Operating system:
Language/runtime version:
Application version:
```

# 💻 Coding Standards

Every project may define its own coding standards.

However, contributors should generally aim for code that is:

* Readable.
* Maintainable.
* Consistent.
* Well structured.
* Appropriately documented.

Avoid unnecessary complexity.

Prefer clear solutions over clever solutions that are difficult to understand.

For example:

```text
Good code should make its purpose understandable.
```

Variable names should be meaningful.

Prefer:

```javascript
const activeUsers = getActiveUsers();
```

Instead of:

```javascript
const x = getUsers();
```

Unless the context makes the meaning obvious.

---

# 📖 Documentation Standards

Documentation is part of the project.

If a feature changes how users install, configure, or use the software, relevant documentation should be updated.

Do not submit a major feature without considering whether documentation needs to change.

Documentation should be:

* Clear.
* Accurate.
* Easy to follow.
* Updated when the software changes.

---

# 🧪 Testing Expectations

Not every contribution requires the same level of testing.

However, contributors should test their changes before submitting a Pull Request.

Depending on the project, testing may include:

* Unit tests.
* Integration tests.
* End-to-end tests.
* Manual testing.
* Performance testing.

If automated tests exist, contributors should avoid breaking them.

New features should include tests when appropriate.

# 🎓 Academic Integrity and Coursework

This is one of the most important rules in this organization.

The organization must **never become a place for cheating, plagiarism, or submitting someone else's work as your own**.

Students must follow University of the People academic integrity requirements.

## Coursework Should Not Be Shared for Copying

Do not use this organization to:

* Upload answers to active assignments for other students to submit.
* Share completed work for the purpose of copying.
* Request someone to complete your coursework.
* Submit another contributor's work as your own.
* Collaborate on individual assignments when collaboration is not permitted.
* Share exam answers.
* Share restricted assessment materials.

---

## Learning Together Is Encouraged

There is an important difference between:

```text
Helping someone understand a concept
```

and:

```text
Completing their assignment for them
```

Members are encouraged to:

* Explain concepts.
* Share learning resources.
* Discuss programming techniques.
* Help debug general problems.
* Review code when collaboration is permitted.

However, every student remains responsible for their own academic work.

---

## University Assignments and Public Repositories

Before publishing coursework, students should consider:

* University rules.
* Assignment requirements.
* Whether the work is currently being assessed.
* Whether publishing the solution could enable academic dishonesty.

When in doubt, do not upload active assignment solutions to public repositories.

# 🔐 Security and Privacy

Never commit sensitive information.

Examples include:

```text
API keys
Passwords
Private keys
Database credentials
Access tokens
Production environment files
Personal information
```

Never commit:

```text
.env
.env.production
private.key
credentials.json
```

unless the repository explicitly uses a safe example file.

Instead, use:

```text
.env.example
```

Example:

```env
DATABASE_URL=
API_KEY=
JWT_SECRET=
```

If you accidentally expose a secret:

1. Revoke or rotate the secret immediately.
2. Inform the repository maintainers.
3. Do not simply delete the secret and assume it is safe.

Secrets committed to Git history may remain accessible.

Security vulnerabilities should not always be reported through public issues.

Repositories should provide guidance through their `SECURITY.md` file.

# ⚠️ Violations and Enforcement

Violations of these rules may result in actions including:

1. A private warning.
2. A request to correct the behavior.
3. Removal of repository access.
4. Temporary suspension from the organization.
5. Permanent removal in serious cases.

Serious violations may result in immediate removal.

Examples include:

* Harassment.
* Deliberate sabotage.
* Repeated academic dishonesty.
* Publishing private contributor information.
* Deliberately introducing malicious code.
* Repeated abuse of community members.

Maintainers should apply rules fairly and document serious decisions where appropriate.


## Step 9: Open a Pull Request

Clearly explain what you changed.

Be prepared to receive feedback.

Code review is part of the learning process.
